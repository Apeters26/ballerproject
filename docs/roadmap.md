# Autonomous drone simulator roadmap

**Planning status.** This is a proposed sequence for two collaborators. A milestone closes when its evidence is attached to the implementation pull request. Milestones express dependencies and exit criteria rather than calendar commitments.

**First release.** On a CPU laptop, one simulated quadcopter takes off, flies through five gates in order and lands. Either collaborator can watch a live run, repeat it headlessly and inspect a saved flight offline. The [product specification](product-spec.md) defines the flight experience and acceptance criteria. The [technical specification](technical-spec.md) defines the course, timing, scoring, artifacts and verification procedure.

## Deliver the first autonomous flight

Contributor A owns the simulated world and judging. Contributor B owns flight control and the operator experience. They review each other’s fixtures and swap machines for release acceptance. The split lets both work against the same course and observation contract without waiting for a working autopilot.

| Milestone | Depends on | Contributor A | Contributor B | Evidence required to advance |
| --- | --- | --- | --- | --- |
| M0 · Agree on the flight contract | Specs reviewed | Check in the fixed course and document its coordinate frame, gate order and landing pad. | Define the controller input/output contract and how an operator starts a run. | Both contributors can identify the intended outcome of a hand-drawn route through all five gates, a route that clips a frame, and one that lands too early. Translate those examples into test fixtures. |
| M1 · Establish physics and judging | M0 | Bring up the CPU physics world, gate bodies and fixed simulation clock. Implement gate crossing and contact decisions with synthetic trajectories. | Bring up the baseline controller, first for takeoff and hover. Capture time and position for inspection. | A headless smoke run steps the real physics engine. Unit tests distinguish a valid crossing from a reversed, out-of-order or clipped crossing. A live hover produces a readable state trace. |
| M2 · Complete the mission | M1 | Integrate the judge, timeout, termination reason and landing checks. Review traces at each gate. | Implement guidance through each gate, approach to the pad and controlled touchdown. | Commit the run command and attach a successful five-gate flight summary. Demonstrate that an induced failure reports a specific reason and cannot count as a successful flight. |
| M3 · Make flights inspectable | Artifact contract from M0; accepted run from M2 for final verification | Check saved event order, timestamps and terminal result against the judge. Exercise a failed run. | Wire live visualization and offline replay to the same flight data. Document setup, run, replay and troubleshooting. | The second contributor identifies where a failed flight ended using its saved artifacts alone. The headless and visual runs meet the equivalence criteria in the technical spec. |
| M4 · Release the MVP | M2 and M3 | Run automated acceptance on a clean environment and archive the result with its course and software identifiers. | Run the documented demo and replay on a representative CPU laptop. Record the platform, runtime and any setup issues. | Another collaborator can install from the repository, reproduce the nominal mission, inspect the scored landing, and replay the saved trajectory. Attach the release checklist and evidence to the PR. |

## What to build after the MVP

Choose the next phase by the question the current version cannot answer. Keep the reference course and baseline controller available as regression fixtures as new capabilities arrive.

| Priority and dependency | Question for the operator | Smallest useful addition | Evidence to advance |
| --- | --- | --- | --- |
| 1 · Compare controllers, after M4 | Did my controller improve the same flight? | Add a second interchangeable controller and a local comparison report. Run controllers independently on identical inputs and physics settings. Sort by mission success first and elapsed simulated time for successful flights. Show failure reasons alongside results. | A collaborator can reproduce the comparison from the recorded configurations. A controller that skips a gate cannot outrank one that finishes. Equivalent controllers tie. |
| 2 · Vary the course, after comparable runs | Does the controller generalize beyond the route we tuned? | Add seeded gate layouts and static obstacles. Reject courses with intersecting gates or blocked designated passage. Keep separate development and evaluation seed lists. | Both controllers receive the same accepted courses and start conditions. Regenerating a seed reproduces its layout. Report completions out of attempts, paired per-course outcomes and times for courses both controllers completed. |
| 3 · Stress sensing and control, after varied courses | Why does a route that works in still air fail when conditions change? | Introduce one disturbance at a time, starting with wind, then observation noise, delay or dropout. Give the controller only the selected sensor observations while the judge keeps simulator ground truth. | With effects disabled, the reference flight still passes. For each effect, replay a failure with its recorded intensity and seed. Publish completion rates by intensity with sample counts. |
| 4 · Try a learned policy, after the benchmark is stable | On which courses or disturbances does learning beat the baseline? | Prototype imitation learning from baseline flights or a small reinforcement-learning policy. Train on development seeds within a declared compute budget. Preserve the same observation and action limits during evaluation. | Lock the policy and evaluation protocol before exposing the held-out results. Compare against the classical controller on identical scenarios, reporting completion, paired flight times, training cost and CPU inference time. Adopt a learned policy only if the observed gain justifies the added cost. |
| 5 · Fly multiple drones, after single-drone judging and benchmarking | Can two controllers share a course without collisions or interference? | Start with two virtual drones, fixed starts, independently attributed gate progress and explicit collision rules. Learned control is optional. | A replay identifies which drone crossed each gate. Scripted tests exercise contact between drones, independent completion and a single-drone regression. |
| Optional controller research, after phases 2–3 | Can an AI suggest a navigation change and show when it helps? | Give an AI Inventor the controller interface and a fixed trial budget. Let an AI Scientist propose a specific test, such as whether slowing before tight turns improves completion in crosswinds. Record unsuccessful candidates as well as improvements. | Run candidate controllers in isolation against a fixed judge. Lock the predicted effect and candidate before testing held-out courses. Keep a change only when another collaborator can reproduce the comparison, including the flight-time cost of any gain in completion. |
| Optional hardware feasibility, separate decision after phase 3 | Which assumptions survive outside simulation? | If the collaborators choose hardware, first identify an airframe and control interface, run software-in-the-loop with flight firmware, and review simulator-to-hardware discrepancies. | Require a separately approved test plan covering operator override, loss of link, operating area and safe shutdown before any physical flight. Hardware procurement and flight trials require their own scope and budget. |

## Operating the roadmap

- Open one implementation issue per milestone with the prerequisite, acceptance fixture, owner and reviewer. A small PR should include the command to reproduce its evidence and a link to the governing requirement.
- Use synthetic trajectories to debug judging and real simulated flights to debug control. When a controller change improves its time, review the event trace and completion status before accepting the improvement.
- Keep benchmarking local until repeat runs on a CPU laptop become a measured bottleneck. Record elapsed wall time for compute planning and elapsed simulated time for comparing flights. Consider GPU or remote training only if a selected learning experiment needs it.
